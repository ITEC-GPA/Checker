TRENO DI RILASCIO DELLE LIBRERIE GPC
Regole del 10/10/2026 (revisione di architettura, punto R3, e decisioni dell'utente).

PERIMETRO E DIREZIONE DELLE DIPENDENZE
Utilities <- Geometry (GPCGeometry, DelaunayMesh) <- Model (GPCModel, GPCModelData,
GPC.Model.Persistence, GPC Converter) <- Checker (Concrete, Steel, CompositeBridge,
Geotechnics, GPCModelChecker) <- ANTHEA. Nessuna dipendenza all'indietro: Model fissa
solo Geometry e Utilities; ModelChecker sta in Checker.

REGOLE
1. Versioni (delega dell'utente, 12/10/2026). L'agente sceglie in base alle modifiche:
   ultimo componente incrementato per i fix; secondo componente da sinistra incrementato
   e successivi azzerati negli altri casi. Esempi: 0.0.27.1 -> 0.0.27.2 (fix),
   0.0.27.2 -> 0.1.0.0 (altro). Motivo e numero entrano in un commit dedicato, anche
   sul branch candidato. Nessuna conferma sul numero; merge e push restano autorizzati
   separatamente. Nessuno strumento cambia le versioni da solo.
2. Un solo treno. Si rilascia un set coerente di commit dei quattro repository, mai
   una libreria isolata. Se cambia Model, il set comprende il Checker compilato contro
   quel Model.
3. Il set lo produce build/Release-Set.ps1 da checkout puliti: controlla che Model fissi
   i binari committati di Geometry e Utilities del set, esegue tutte le suite, copia le
   dodici DLL e scrive release-set.json (versioni, SHA-256, commit, esiti delle suite).
4. Nessun rilascio senza tutte le suite verdi: Model (Core, UnitTest, API), Checker
   (Concrete e Steel net472, CompositeBridge, Geotechnics, Calculation, ModelChecker,
   API). Sono ammessi solo i fallimenti elencati per nome in build/known-failures.json.
5. Una DLL con SHA-256 diverso dal set precedente deve avere una versione piu' alta:
   Release-Set.ps1 -Previous rifiuta il set altrimenti. Due build diverse non possono
   avere la stessa versione.
6. Build deterministiche (Directory.Build.props): gli stessi commit danno gli stessi
   SHA-256 in qualunque cartella. Le ricette con cartelle fisse non servono piu'.
   Gli a capo entrano negli hash del PDB e quindi nella DLL: .gitattributes di Model e
   Checker fissa CRLF ("* text=auto eol=crlf") e Release-Set.ps1 rifiuta i file con a capo
   diversi da un checkout pulito (per esempio scritti con LF da uno strumento).
7. ANTHEA installa lib/Checker solo da un set di rilascio
   (tools/libs/Update-Snapshot.ps1 -ReleaseSet <cartella>), che ricontrolla gli SHA-256.

PROCEDURA
a. Lavoro su un branch da master aggiornato; suite del repository toccato.
b. Merge su master con l'ok dell'utente.
c. L'agente assegna le versioni delle DLL cambiate secondo la regola 1; il commit di
   versione puo' essere preparato sul branch e confluisce in master al merge autorizzato.
   Utilities e Geometry ricompilano in Release e committano bin/Release; Model aggiorna
   in build/dependencies.props versioni e SHA-256 di Geometry e Utilities.
d. Release-Set.ps1 -Root <checkout puliti> -Out <cartella nuova> -Previous <set precedente>.
e. Push dei commit con l'ok dell'utente; poi in ANTHEA Update-Snapshot.ps1 -ReleaseSet
   <cartella> -Install, profilo full del runner e voce nel README di lib/Checker.

SET CANDIDATO
Release-Set.ps1 -Candidate ammette branch e commit non pushati e salta il controllo
delle versioni: il set e' marcato candidate. ANTHEA lo installa solo con -AllowCandidate,
per prove su branch, mai come rilascio.
